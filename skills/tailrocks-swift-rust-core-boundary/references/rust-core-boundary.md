# The Rust core boundary

Applies when the application keeps its behavior in a Rust core behind a thin
SwiftUI shell. This is the **mandated** house architecture for a native app
that pairs Rust with a Mac or iOS interface: SwiftUI owns the pixels and
native interaction semantics; Rust owns what the application actually does —
the domain model, state transitions, validation, persistence, networking,
synchronization, background computation, permissions policy, and business
rules. It does not replace the SwiftUI-first rule — the shell is still real
SwiftUI describing every screen — it bounds what the Swift code is *for*.

The Swift layer is an **Apple platform shell, not only a thin UI layer**.
Some nonvisual capabilities — StoreKit, BackgroundTasks, WidgetKit, App
Intents, notification authorization, Keychain, security-scoped files — are
inseparable from Apple's lifecycle and entitlement model. Their *mechanism*
belongs in Swift as narrow adapters; every *product decision* around them
stays in Rust. The adapter contract, the per-framework splits, and the iOS
lifecycle rules live in
[`apple-platform-shell.md`](apple-platform-shell.md); read it whenever a
feature touches an Apple-only capability.

Corollaries: no Objective-C source and no handwritten C bridge — the
C-compatible ABI exists but is generated by the bridge; begin with SwiftUI
only, adding an AppKit adapter only after a documented SwiftUI limitation
(this skill's interop rules).

"Minimal Swift" means minimal *responsibility*, not minimal line count. A
UI-heavy app still describes every screen in Swift; those lines are limited
to declaring native controls and layouts, rendering immutable state from
Rust, translating gestures into semantic actions, presentation details,
native localization and accessibility, and the platform adapters above. The
health test for the boundary: **could the entire SwiftUI shell be replaced
by another frontend without rewriting product behavior?** When the answer
is yes, the boundary is healthy.

The renderer is not a choice: **it is always Apple's modern,
Apple-recommended one — SwiftUI on the system rendering stack.** Never use
GPUI or anything similar in a native Swift app; a second UI system makes
Liquid Glass, accessibility, menus, focus, and window behavior harder and
inherits nothing from future OS releases. A high-performance custom region
is drawn with Apple's own rendering — `Canvas`, SwiftUI Metal shader
modifiers, or a justified `MTKView` boundary — per
`tailrocks-macos-design`'s custom-renderer rule.
A dynamic "Rust sends a UI schema, Swift renders it generically" design is
rejected for the same reason: it rebuilds an inferior UI framework and loses
SwiftUI's compile-time behavior, accessibility, previews, and design
adaptation.

## The named anti-model: Swift MVVM with Rust repositories

The most common hybrid shape is a Swift view model per screen that owns
validation, loading state, retries, permissions, and navigation decisions,
and calls Rust "repositories" for storage and networking. Reject it by
name. The view models gradually become the real application, Rust is
demoted to a helper library, and the two sides end up duplicating state
models, error handling, validation, loading and retry rules, permissions,
selection behavior, navigation decisions, cache invalidation, and
synchronization state.

The correct flow: SwiftUI interaction → typed `AppAction` → Rust
application actor (domain transition, I/O, effects) → immutable
presentation state → SwiftUI render. SwiftUI is a renderer and interaction
translator; Rust determines what an interaction *means*. Swift sends
`.renameCommitted(itemID:proposedName:)`; Rust decides whether the name is
valid, whether the item can be renamed, whether it conflicts, whether the
change is optimistic, whether persistence succeeded, whether sync is
required, and what state or error to display. A Swift store's only
mutations apply Rust snapshots or manage transient presentation — it is
never a second application reducer.

## Responsibility split

| Concern | Owner |
|---|---|
| `App`, scenes, windows, commands, settings scene | SwiftUI |
| Navigation containers, toolbars, sidebars, inspectors | SwiftUI |
| Liquid Glass, animations, focus, keyboard shortcuts, accessibility | SwiftUI |
| Sheets, alerts, popovers; hover, scroll position, animation phase | SwiftUI |
| Raw text buffer while a person is actively typing | SwiftUI |
| Localized wording, plurals, locale-aware date/number/currency display | SwiftUI (`FormatStyle`, String Catalogs) |
| StoreKit, Keychain, notifications, BackgroundTasks, file pickers — mechanism | thin Swift adapters ([`apple-platform-shell.md`](apple-platform-shell.md)) |
| Widgets and App Intents entry points | thin Swift targets |
| Domain entities, invariants, validation, permissions | Rust |
| Application state machine and transitions | Rust |
| Networking, retry, authentication, synchronization | Rust |
| Persistence, migrations, cache, search, indexing | Rust |
| Background computation and concurrency; undo semantics | Rust |
| Durable pending platform effects; recovery and checkpointing | Rust |
| Error codes and recoverability | Rust |
| Subscription and entitlement policy | Rust |
| FFI conversion code | generated, never handwritten |

Swift never contains database queries, network calls, business validation, or
a duplicated domain model. Rust never composes user-facing English strings —
it sends semantic codes and values; the shell localizes and formats.

## The message boundary: five concepts

Do not expose the Rust object graph — no `Database`, `Repository`,
`HttpClient`, `AuthenticationManager`, cache, or domain aggregate internals
ever cross the boundary. Swift sees one cohesive application API built from
five message concepts:

1. **`AppAction`** — Swift → Rust. Every user interaction becomes one typed
   value carrying *product semantics*, never widget events:
   `renameCommitted`, `deleteConfirmed`, `filterCommitted`,
   `retryRequested` — not `buttonTapped`, `rowIndexChanged`, or
   `textFieldDidEndEditing`, which couple Rust to one SwiftUI
   implementation. Lifecycle is also semantic: `started`, `becameActive`,
   `enteredBackground`.
2. **`ViewState`** — Rust → Swift. An immutable, UI-ready projection —
   never the domain model. Rust decides which actions are enabled, which
   records are visible, which semantic status applies, whether retry is
   available. Swift decides fonts, padding, animation, glass style, native
   control choice, localized phrasing, and locale-sensitive formatting.
   Snapshots are **feature-scoped** (sidebar, content, detail, sync
   status), not one whole-app value: replacing one giant observed value
   invalidates every view that reads any part of it, and shipping the whole
   tree re-encodes every string and collection at the boundary on every
   change.
3. **`UpdateNotice`** — Rust → Swift, as a stream. A lightweight
   invalidation — `revision` plus `changed_features` — **never the state
   itself and never a business event log**. Bridge streams are backed by a
   bounded per-subscription ring buffer that **drops new events when
   full**; treat every streamed notification as lossy. The resilient
   protocol: Rust increments the revision and pushes a notice; Swift pulls
   the latest snapshot for each changed feature and applies it only if
   newer than the last applied revision. A lost notice self-heals on the
   next notice, and Swift performs a **full snapshot reconciliation on
   launch, reconnection, and foreground activation**.
4. **`PlatformEffect` / `PlatformEffectResult`** — Rust asks Swift to
   execute an Apple mechanism (purchase, store a secret, request
   notification authorization, schedule background refresh, import a
   document). Effects live in a **durable Rust queue until acknowledged**
   via a completion call; Swift also drains `pendingPlatformEffects()` on
   activation, so a dropped stream event or a backgrounded process never
   loses an effect. Effect execution is idempotent per effect ID, and one
   effect ID is never executed twice concurrently. Details:
   [`apple-platform-shell.md`](apple-platform-shell.md).
5. **`CoreError`** — Rust → Swift as a typed error with a semantic code and
   structured payload (`permissionDenied(permission:)`,
   `conflict(currentRevision:)`, `temporarilyUnavailable(retryAfter:)`).
   Swift maps codes to String Catalog entries, native alert wording,
   pluralization, and formatting. No localized English is constructed in
   Rust.

## The dispatch contract

The default boundary call is a **fast synchronous enqueue**:

```rust
pub fn dispatch(&self, action: AppAction) -> Result<(), DispatchError>
```

It validates the boundary-level shape, puts a command on the actor's
channel, and returns. It must never access the network, run migrations,
parse a large document, block on a long-held lock, or wait for another
actor. The UI thread never blocks on product work.

Use `async throws` only for a bounded request that naturally returns one
result (`exportDocument`, `generatePreview`, `loadNextSearchPage`).
Cancellation propagates to the Rust future but is cooperative: code after
an `await` may never run after cancellation, so cleanup and durability must
not depend on reaching it. Streams carry only `UpdateNotice`. A callback
trait is a rare integration where Swift must supply a service directly.

## The store rule

Exactly one `@MainActor @Observable` store owns the generated core handle.
Views receive immutable view-state plus a `send` closure and never see the
FFI. Infrastructure — the core handle, the effect handler, the subscription
task — is `@ObservationIgnored`; observed properties are the feature-scoped
snapshots.

```swift
@MainActor @Observable
final class AppStore {
    @ObservationIgnored private let core: AppCore   // the only reference anywhere
    @ObservationIgnored private let effects: PlatformEffectHandler
    @ObservationIgnored private var updatesTask: Task<Void, Never>?
    @ObservationIgnored private var appliedRevision: UInt64 = 0

    private(set) var sidebar: SidebarViewState
    private(set) var content: ContentViewState
    private(set) var detail: DetailViewState
    private(set) var syncStatus: SyncStatusViewState
    var presentedError: PresentedError?

    init(core: AppCore, effects: PlatformEffectHandler) {
        self.core = core
        self.effects = effects
        sidebar = core.sidebarSnapshot()
        content = core.contentSnapshot()
        detail = core.detailSnapshot()
        syncStatus = core.syncStatusSnapshot()
    }

    func start() {
        guard updatesTask == nil else { return }
        updatesTask = Task { [weak self] in
            guard let self else { return }
            for await notice in core.updates() {
                guard !Task.isCancelled else { break }
                apply(notice)
                await drainPlatformEffects()
            }
        }
        reconcileAllState()
        send(.started)
    }

    func stop() {
        updatesTask?.cancel()
        updatesTask = nil
    }

    func send(_ action: AppAction) {
        do { try core.dispatch(action: action) }
        catch { presentedError = PresentedError(error) }
    }

    private func apply(_ notice: UpdateNotice) {
        guard notice.revision > appliedRevision else { return }   // stale
        appliedRevision = notice.revision
        for feature in notice.changedFeatures {
            switch feature {
            case .sidebar: sidebar = core.sidebarSnapshot()
            case .content: content = core.contentSnapshot()
            case .detail: detail = core.detailSnapshot()
            case .syncStatus: syncStatus = core.syncStatusSnapshot()
            case .platformEffects: break
            }
        }
    }

    private func reconcileAllState() { /* pull every snapshot */ }
    private func drainPlatformEffects() async { /* see apple-platform-shell.md */ }
}

struct ItemListView: View {
    let state: ContentViewState
    let send: (AppAction) -> Void
    // body reads state and calls send; it cannot reach the core
}
```

A large application may split into small feature stores
(`SidebarStore`, `DetailStore`) — still `@MainActor @Observable`, still
zero business logic, each exposing one narrowly scoped Rust snapshot.

Prohibitions, each a review finding:

- No view holds or calls the core; no FFI call from `body`.
- No single giant `state: EntireApplicationState` property — feature-scoped
  snapshot properties, so one change does not invalidate every view.
- Never capture the core in `Task.detached` or pass it between arbitrary
  actors; dispatch is synchronous enqueue from the main actor. The
  subscription task is created from the store (`Task { … }`), inheriting
  main-actor isolation.
- Never mark a generated type `@unchecked Sendable` without auditing the
  generated implementation and writing the justification — bridge
  generators have known `Sendable` gaps. Keep the generated handle
  encapsulated in the main-actor store instead.
- No `ObservableObject`/`@Published`/Combine for new state; the model is
  `@Observable` + `@State` + environment, with `@Bindable` only where a
  genuine Swift-side binding exists.
- Previews and view tests construct sample view-state values with a no-op
  `send`; a preview never needs the Rust runtime, a database, the network,
  or the XCFramework. Only `AppStore` ever touches the real core.

## State placement

Swift owns state that exists because a native interface is currently being
presented; Rust owns state that exists in the product regardless of the
interface. Transient presentation mechanics stay in the shell (`@State`,
`@FocusState`): open popover, hover target, focused field, drag preview,
scroll position, animation phase, window geometry, a sheet's form before
submission, the live text buffer. Durable and semantic state lives in Rust:
loaded records, semantic selection, validated filters, preferences, auth
and sync state, subscription status, pending operations, undoable
operations, persistent workspace state, error and retry state.

Text editing: never one FFI round-trip per keystroke unless the feature
needs it. Keep the buffer in SwiftUI; send a debounced query, a committed
value on Enter, and a semantic save action. A document editor that must see
every edit batches deltas, not per-character round-trips.

Navigation: Rust owns the semantic destination (selected entity, requested
settings section, resolved deep-link target, permission to open it);
SwiftUI owns native presentation (`NavigationPath`, column visibility,
sheet versus push, sidebar collapse). A deep link flows: Swift parses the
platform URL shape → typed action to Rust → Rust validates and resolves the
domain target → view state carries the destination → Swift presents it
natively. The same Rust route may render as a three-column split on macOS,
two or three columns on iPad, and a stack on iPhone.

## Runtime shape

One application runtime, created once — never a runtime per FFI call: one
long-lived async runtime (Tokio when infrastructure needs it — `reqwest`
and async file I/O require a live reactor), one application actor fed by a
command channel that serializes authoritative state transitions, services
free to run concurrently underneath and report back as messages, and a
shutdown call that cancels work and flushes durable state. A single logical
writer gives predictable ordering, easy testing, clear cancellation, and no
competing writers — it does not make the application single-threaded.

The exported core class stays `Send + Sync` (the bridge default); never use
a `single_threaded` escape hatch for the application core. The mutable
model lives inside the actor, not behind a giant shared mutex. The
constructor is fast — create channels, runtime, initial "starting"
snapshot, spawn the actor, return; migrations, network restoration, and
cache loading happen after startup inside Rust, never blocking the main
actor during `AppCore` creation.

Multi-window and iPad multi-scene: one shared Rust runtime (database,
networking, auth, cache), one Rust window/scene session per window
(selection, navigation, search), one Swift store per scene — never a single
global store across `WindowGroup` windows or a process-wide singleton
holding scene-specific selection. Document-based apps add a small Swift
document wrapper; parsing, serialization, validation, migration, and
document semantics stay Rust-owned.

On iOS the runtime does not evade suspension — backgrounding stops all
progress. Checkpointing, resumable operations, and the scene-phase protocol
are in [`apple-platform-shell.md`](apple-platform-shell.md).

## FFI performance

Primitive crossings are cheap; strings allocate and copy, records are
copied, and large collections of string-bearing records dominate call cost.

- **Never cross the boundary at rendering frequency.** No FFI on animation
  frames, pointer movement, scroll offsets, hover transitions, continuous
  drag positions, layout measurement, or every keystroke.
- **Coarse-grained snapshots, never per-field getters.**
  `contentSnapshot(page:pageSize:)` — not `itemCount()` /
  `itemTitle(at:)` / `itemIsEnabled(at:)`, which turn each row into
  multiple FFI calls.
- **Large binary data goes by file URL.** Rust writes images, exports, and
  archives to a temporary or cache file and returns the URL plus metadata;
  `Data` crossings are for small payloads only.
- **Coalesce progress.** Rust may generate thousands of internal progress
  events; the UI needs perhaps 5–20 updates per second.
- **Profile both sides** on release builds: the Instruments SwiftUI
  instrument (long `body` evaluations, unnecessary updates), Time Profiler,
  Hangs, Rust `tracing`, and signposts around FFI calls, watching snapshot
  size and update frequency.

## Bridge selection

Verified 2026-08-16; bridge generators move fast — re-verify at execution
time and pin exactly (toolchain, bridge crate, bridge CLI; see
`tailrocks-swift-rust-core-setup` for the pins, the split
package layout, and the binding-drift gate).

- **BoltFFI** — first choice: attribute-driven exports (`#[data]`,
  `#[error]`, `#[export]`, stream attributes), Swift `async`/`throws`,
  `AsyncStream` for Rust streams with cancellation propagation, automatic
  XCFramework + local Swift package. Fast-moving; known open issues around
  generated `Sendable` and multi-module Apple packaging — pin exactly
  (0.30.0 at verification) and keep one FFI module.
- **UniFFI** — conservative fallback: production-quality Swift generation,
  more established; Swift 6 strict-concurrency support still partial. Choose
  it when bridge stability outweighs packaging convenience or BoltFFI hits a
  blocking issue.
- **swift-bridge** — not the default: efficient but low-level, with an
  incomplete type surface and more manual integration.
- **Crux** — borrow the event/state/view-model shape, do not adopt: its
  side-effect-free core pushes I/O into Swift, the opposite of this split.

Keep bridge annotations out of domain crates: dedicated contracts and FFI
crates define the boundary records and enums, so replacing the bridge is a
contained change. Only the handwritten bridge package imports the generated
module; the rest of the Swift tree depends on the bridge package.

## Testing split

Nearly all behavior tests run in Rust without Xcode: domain units, property
tests for invariants, action → state transition tests
(`dispatch(action) … assert snapshot`), database migration and repository
tests, network contract tests, conflict-resolution, outbox and retry,
cancellation, checkpoint/recovery, **platform-effect idempotency**, and
**lost-stream-notice reconciliation** (drop notices, assert the next pull
converges). The Swift side keeps: snapshot application and **revision
ordering** in the store, action conversion, platform-effect execution
against fake services (a `FakePurchaseService` proves the mechanism is
invoked and the normalized result returned — never purchase policy),
error-to-localization mapping, menu and command enablement, accessibility
checks, an XCFramework integration smoke test, and a few critical
end-to-end UI flows. Every feature view is previewable from sample state
with a no-op `send`. A new business rule without a Rust test is unfinished.
