# Rust-core lane

Applies when the application keeps its behavior in a Rust core behind the
SwiftUI shell (the boundary contract itself is
`tailrocks-swift-rust-core-boundary`'s; Rust workspace
mechanics are `tailrocks-rust-project-setup`'s). This lane adds what the
Apple baseline must additionally pin, generate, and gate.

## Layout

The Rust workspace and the Apple projects live in one repository; app
projects stay generated and uncommitted exactly as required by
`tailrocks-swift-project-setup`'s project-generation policy:

```text
app/
├── Cargo.toml               # workspace
├── Cargo.lock
├── rust-toolchain.toml
├── mise.toml                # one task set drives both halves
├── crates/
│   ├── domain/              # entities, invariants — no FFI knowledge
│   ├── application/         # actions, actor, state transitions, effects
│   ├── infrastructure/      # HTTP, database, cache, telemetry
│   ├── apple-contracts/     # boundary records: actions, view state,
│   │                        #   platform effects, errors
│   └── apple-ffi/           # exported core class, sessions, conversions
└── apple/
    ├── Packages/
    │   ├── AppCoreBindings/        # generated by the bridge — never edited
    │   ├── AppCoreBridge/          # handwritten Swift isolation layer
    │   ├── AppPresentation/        # shared SwiftUI views on value types
    │   └── ApplePlatformServices/  # StoreKit, Keychain, files, tasks
    ├── macOSApp/            # project.yml; generated project stays ignored
    ├── iOSApp/              # when the product ships iOS
    ├── WidgetExtension/
    └── AppIntentsExtension/
```

Only `apple-contracts` and `apple-ffi` know the bridge exists — boundary
records and enums are defined there, never annotated onto domain types.
Domain, application, and infrastructure crates must not know Swift exists;
replacing the bridge is then a contained change. Keep **one FFI module** in
one dedicated crate: multi-module Apple packaging has open bridge issues —
do not split until the pinned version verifiably supports it.

Swift dependency direction is one-way and fixed:

`AppCoreBindings` (generated) → `AppCoreBridge` (handwritten) →
`AppPresentation` → app targets. **Only `AppCoreBridge` imports the
generated module.** App code and views depend on the bridge package, so a
bridge swap or regeneration never ripples through the SwiftUI tree.

## Cargo configuration

The FFI crate builds as a static library, and release builds keep debug
info so the bridge can produce a symbols archive for native crash
symbolication:

```toml
[lib]
crate-type = ["staticlib"]

[profile.release]
lto = "thin"
codegen-units = 1
debug = true
```

## Pins

`mise.toml` remains the single tool authority. Pin, exactly:

- the Rust toolchain (`rust-toolchain.toml`, channel + components);
- the bridge crate version (workspace `Cargo.toml`, exact `=` requirement);
- the bridge CLI version (mise-managed, never a floating install) — crate
  and CLI pinned to the **same** version.

Bridge generators are pre-1.0 and move fast (BoltFFI 0.30.0 at
verification, 2026-08-16 — re-resolve at execution time); an unpinned CLI
regenerating different Swift on two machines is the supply-chain version of
the false-green trap. A bridge upgrade is a dedicated change — bump the
pins, regenerate the bindings, run the full Apple-target test set — never
an incidental update inside a feature branch.

## Packaging

The bridge CLI builds the device, simulator, and macOS slices, then
produces an XCFramework plus a generated local Swift package; Xcode
consumes that package as a **local** SwiftPM dependency — never a registry
fetch of your own bindings. When the generator offers package layouts,
choose the **split** layout: it leaves the wrapper target to the
handwritten `AppCoreBridge` package instead of spreading generated code
through the app. The packaging step is a mise task (for example
`mise run bridge`), ordered before `generate` in the task chain so a clean
checkout builds with the standard task sequence. Build both `arm64` and
`x86_64` unless the project has recorded an Apple-silicon-only decision.

## Gates

Additions to the baseline gate set:

- **Binding-drift gate.** CI regenerates the bindings and fails when the
  generated Swift differs from what is committed (or, if generated output
  is intentionally uncommitted, when regeneration changes the package
  interface) without an intentional bridge change. Silent binding drift is
  how an action added in Rust ships unreachable from the UI.
- **Rust test lane.** The behavior tests live in the Rust workspace and run
  with the standard Rust gates — no Xcode required. The Apple CI job runs
  them alongside the Swift build so a domain regression fails the same
  pipeline that ships the shell.
- **Ordered pipeline.** Rust gates first (format, clippy, tests), then the
  exact-pinned bridge CLI packs the XCFramework, then the drift gate, then
  Swift packages build under Swift 6 strict concurrency, then macOS and —
  when the product ships iOS — iOS-simulator build-and-test on the stable
  Xcode lane, then the critical UI smoke tests. Archive the XCFramework
  symbols and app dSYMs from release builds.
- **Beta lane is nonblocking.** The forward-validation Xcode lane from
  `tailrocks-swift-project-setup`'s toolchain policy also builds this stack,
  and its failures never gate the
  shipping pipeline.
