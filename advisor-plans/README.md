# Advisor Plans — Native `/goal`, Verifiable Acceptance

Generated by the `improve` skill on 2026-08-09; adversarially reworked on
2026-08-10 at commit `b629fb9` (second draft), then re-audited the same day by a
third adversarial pass — two independent reviews plus a steelman defense of the
second draft; see RESEARCH.md "Third adversarial pass" for what changed and,
just as importantly, which proposed simplifications were rejected. This
repository reserves `plans/` for Tailrocks delivery packages, so these
implementation handoffs live in `advisor-plans/`. See
[RESEARCH.md](RESEARCH.md) for evidence, rejected alternatives, trust limits,
and full user-goal coverage.

The revised target is deliberately narrower and more truthful than the first
draft:

> Agents propose. A small trusted kernel decides whether frozen evidence passes.
> Determinism belongs to the decision over that evidence, not to model output,
> semantic judgment, or an unrestricted local host.

Native `/goal` remains the user-facing loop. Codex is the only initial runtime.
Grok and Claude are later conformance targets, never assumed compatible. The
controller does not launch a competing agent supervisor.

## Chosen architecture

The first draft built ten horizontal layers before proving the native-provider
boundary. It also had an execution cycle: oracle anchoring in 004 depended on
005, clean replay in 005 depended on 006, and 006 depended on 005. The revised
sequence is a provider feasibility proof followed by one end-to-end tracer
bullet, then generalization.

```text
native Codex /goal
        |
        v
effective Stop-hook set -----> trusted `tailrocks` checkpoint
                                      |
                                      v
candidate commit/tree -> clean disposable clone -> frozen gates/review evidence
                                      |
                                      v
                           SQLite transaction + receipt
                                      |
                          CONTINUE / BLOCKED / PASS
```

The kernel has five authoritative concepts:

1. `goal.contract.json` — the single runtime contract. It contains requirements,
   plan DAG, allowed repository paths, deterministic gates, review/human seams,
   exact execution resolution, budgets, and digests of every executor-visible
   instruction and protected oracle. Other JSON/Markdown views are generated.
2. Candidate Git identity — each slice receipt binds its base, candidate commit,
   tree, delta, contract, and dependency receipts. A separate package-final
   receipt binds the exact final tree and all current gates.
3. One transactional SQLite journal outside the executor clone — claims,
   transitions, receipts, findings, budgets, and retirement state commit
   atomically. Portable attestations are exported blobs, not parallel logs.
4. Constrained execution and clean verification — executor work occurs in a
   disposable full clone under a preflighted provider sandbox/capability set:
   no extra writable roots, secret-bearing environment, web/search,
   side-effecting MCP/apps/plugins, or agent-usable egress. Verification imports
   the candidate tree into a second disposable clone with sanitized Git and runs
   frozen gates. Linked worktrees are not an isolation boundary. Local mode does
   not promise read confidentiality from other same-user filesystem paths.
5. Explicit trust modes — local mode prevents accidental self-certification but
   is `local_non_adversarial`. Stronger proof requires an operator/CI-owned
   verifier that does not execute PR-head code with credentials.

Version 1 supports serial repository-local changes only. Provider inference
transport is required, but no general network tool, injected credential,
deployment, database, device, IPC, or other external effect is authorized. Such
work is a human/external gate until an enforceable capability broker exists.
Sensitive-host confidentiality requires a dedicated principal/container and is
not part of `local_non_adversarial`.

Three constraints the third pass added to the kernel's definition:

- **Checkpoint fits the hook budget or goes async.** Plan 002 measures the
  maximum Stop-hook wall time and its on-timeout behavior. If clean-clone gates
  exceed it, the hook enqueues verification and returns CONTINUE with a
  poll-and-stop-again prompt; PASS releases only at a Stop with a completed
  current verification. Checkpoint latency is tracked as a product metric — a
  trust tool users bypass for being slow protects nobody.
- **Effective hooks live outside executor-writable roots.** An in-clone hook
  source is a preflight rejection; otherwise the executor can delete its own
  checkpoint and the next Stop never runs it. Checkpoint additionally re-hashes
  the effective hook set to close the mid-session window.
- **Dependencies are controller-provisioned.** Clean-clone gates for the house
  stacks need cargo/bun dependencies; general egress stays disabled while a
  controller-warmed read-only store keyed to lockfile digests is mounted in.
  Registry warming is a labeled controller-side effect.

Provider support is a qualification ladder, not a binary: TIER 0 (kernel CLI +
prose loop, any client), TIER 1 (attended native goal: containment proven,
stop-control weak — false claims surfaced by `tailrocks goal status`, not
intercepted), TIER 2 (unattended: containment and stop-control proven; zero
stop-without-PASS is the Codex release bar). Containment gates every autonomous
tier; acceptance invariants are identical at all tiers. During rollout every
touched skill stays dual-path: full function with no binary present, kernel
authority when it is.

## End-state invariants

- Original user inputs and decisions are immutable records; indexes and README
  summaries are derived and drift-checked.
- Every normative statement maps to a stable requirement. Every requirement maps
  to current evidence, and every observable repository change maps back to an
  authorized plan or explicit prerequisite.
- Every byte shown to an executor is normative and hashed. Copy edits invalidate
  the package unless the executor payload is regenerated.
- One canonical contract defines plan order, scope, gates, budgets, resolution,
  and protected references. No lockstep manifest/coverage/oracle copies exist.
- Executors can claim and submit candidates. They cannot approve anchors,
  integrate candidates, write verified state, create PASS, or retire packages.
- Slice receipts are durable audit evidence bound to base/delta and dependency
  chain; the validity claims are run-ref ancestry plus the package-final
  receipt, which alone equals the final tree with all final gates rerun. There
  is no per-contract selective-invalidation grammar.
- V1 execution is serial. Review may run in parallel; implementation does not.
- Deterministic gates run first in a clean clone. Semantic/product/engineering
  verdicts remain separate and conjunctive, but fresh sessions are required only
  for axes not discharged deterministically or explicitly required by contract.
- A model verdict is an attestation, not deterministic truth. Disagreement or a
  concrete failure blocks; scores and majorities never erase failures.
- At TIER 2, native `/goal` may stop only on a current PASS returned through a
  verified effective hook configuration; conflicting Stop hooks downgrade or
  reject the trust mode. At every tier, PASS itself is kernel-only, and from
  plan 008 the merge-authoritative receipt is the one CI revalidates offline.
- PASS survives retirement failure. Retirement is an explicit, idempotent
  `PASS -> RETIRING -> RETIRED` operator action, not hidden cleanup inside goal
  completion.
- Durable completion contains the final spec, final receipt, and a recoverable
  content-addressed package bundle; branch history alone is not the archive.

## Alternatives considered

| Alternative | Decision | Reason |
|---|---|---|
| Original horizontal formal platform | Reject | Cyclic dependencies, duplicated authority, late feasibility, and no end-to-end value until plan 007. |
| Prompt/Stop-hook hardening only | Reject | Keeps mutable status/oracles and cannot prove scope or current repository state. |
| CI-only acceptance | Later strong mode | Good trust separation, but cannot by itself keep the local native goal loop progressing. |
| Standalone provider supervisor | Reject | Violates the required native `/goal` UX. |
| Thin kernel + staged vertical slices | Adopt | Tests the load-bearing provider boundary first and grows only after a useful end-to-end path exists. |
| Three fresh reviewers for every plan | Reject | Correlated sessions add blocking surface and duplicate deterministic scope checks. Preserve axes, dispatch only unresolved ones. |
| RFC 8785 plus cross-language validators | Reject | One Rust authority needs deterministic bytes, not multiple validators. Hash exact generated bytes and referenced files. |
| Custom subject-tree hashing | Reject | Git already provides canonical tree/commit identities. Bind receipts to Git objects and a separate contract digest. |
| Autonomous non-file effects in v1 | Reject | Post-hoc scans cannot undo or even observe secret reads, network calls, or deployments. |
| Bun/TypeScript kernel instead of Rust | Open decision D2 | No v1 invariant fails under Bun (`bun:sqlite`, same git plumbing, plugin-carried distribution would delete most of plan 009's matrix). Rust stands on strategic grounds: house-stack dogfood, single-binary hook UX without a runtime prerequisite, and the future operator/CI strong-mode verifier where compiled hardening earns real trust. The choice must stay named, not assumed. |
| Binary SUPPORTED/UNSUPPORTED provider verdicts | Reject | All-or-nothing discards the kernel's value on weaker clients. Qualification tiers 0/1/2 keep acceptance invariants identical while making containment non-negotiable and stop-control a UX tier. |
| Per-contract selective receipt invalidation | Reject | Undefined grammar a cold executor would invent. Ancestry plus final-tree rerun with full-delta authorization covers the failure modes with defined semantics. |
| Synchronous checkpoint regardless of hook budget | Reject | Unmeasured hook timeouts turn slow honest verification into uncontrolled stops. Measure the budget (002); enqueue-and-poll when gates exceed it. |
| Ship kernel-dependent skills before the binary ships | Reject | Skills instructing agents to run a nonexistent command regress every plugin channel. Dual-path (prose fallback per plan 000) until 009, and forever on unqualified clients. |

## Open operator decisions

- **D1 — kernel repository split.** Every plugin channel clones this repository
  root, so `crates/`, fixtures, examples, and archives all ship to every skills
  user. Acceptable while the payload is small text; measured and decided at
  plan 009's payload deliverable, where the release machinery a split needs
  exists. Default if the payload is unacceptable: split the kernel into its own
  repository and pin a released binary/version here.
- **D2 — kernel language.** Rust is the working default for the strategic
  reasons in the alternatives table, with the honest caveat recorded there that
  no v1 invariant forces it. Revisit only before plan 003 starts; flipping
  later is a rewrite, which is exactly the drift these plans exist to prevent.

## Proof boundary

Acceptance is deterministic only as a function of frozen inputs and deterministic
verifiers. A semantic model reviewer, human approval, external service, or mutable
environment contributes labeled evidence whose trust and freshness remain in the
receipt. No local mode is called adversary-resistant when executor and verifier
share an unrestricted user account. No credential may be exposed to code from an
untrusted PR head.

## Executor rules

Read a plan fully. Run every precondition and gate. Honor STOP conditions. Use
`rtk` for shell commands. Work on a feature branch. Commit completed changes with
Conventional Commits, `git commit -s`, and
`Co-authored-by: Codex <codex@openai.com>`. Do not push or open a PR unless the
operator asks.
