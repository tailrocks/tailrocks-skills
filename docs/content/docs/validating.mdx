title: Validating, repeatedly
description: "The gates that re-prove shipped work on every round, and the gates that re-prove this collection on every change."
---

Validation here is not an event before a release. It is a loop that runs the
same way every time, at two levels: the work a repository ships, and the
skill collection itself.

## The work: one loop per item

Every roadmap item repeats the same round until nothing blocking remains.
The round is short enough to write on one hand:

1. **The machine gate.** `sh roadmap/<slug>/goal/check.sh` — its final line
   is the fact: `TAILROCKS GOAL: PASS`, or `BLOCKED <reason>`. It hashes the
   frozen contract (`plan-drift`), refuses nonterminal plan rows, and refuses
   a gate that proved nothing (`gate-vacuous`) or one whose proof expression
   is missing (`gate-unproven`). Every gate line is `<command> ||| <proof>`,
   and the proof prints how many units executed — because a test command that
   ran zero tests exits 0 just the same.
2. **The field report.** `tailrocks-record-feedback` captures what you hit,
   verbatim, before anything argues with it.
3. **The execution verdict.** `tailrocks-prove` re-runs every claimed surface
   through subagents and returns a verdict per statement and per plan row.
   What it could not execute is `NOT EXECUTED`, never a pass.
4. **The truth-sync.** `tailrocks-reconcile` re-runs each DONE row's own done
   criteria, rewrites the item's Remaining from the round's blocking defects,
   and sends the item back to execution — or, when a round found nothing
   blocking, writes `DONE` and retires the folder.

The round repeats because the first three steps answer different questions:
the contract ran unedited, you hit these things, execution confirms or
refutes them. None can stand in for another, which is why `PASS` is never
read as done. The full mechanics live in the
[delivery pipeline](/docs/delivery) guide; the point here is that the loop
is the validation, and it costs one invocation per step, every round.

## The collection: gates that never move

This repository validates itself the same way every change, locally and in
CI, with four task names that are a contract rather than a preference:

```sh
mise run lint    # every skill, manifest, and catalog group validates
mise run test    # the script test suite
mise run fmt     # formatting of the TypeScript this repository owns
mise run ci      # lint + generated-file drift check + tests
```

Three more checks sit beside them:

- `mise run docs:check` fails when a generated documentation page or the root
  README's skill table is stale against its
  `SKILL.md` source. Regenerate with `mise run docs`; never edit a generated
  file.
- `claude --plugin-dir .` loads the collection locally, the smoke test that
  the plugin manifests and the skill tree agree.
- `examples/` holds the rendered regression corpus — a complete item folder
  for the pipeline's format, and a macOS screen the family rejected at
  57/100 with the full artifact chain. A change that alters what the skills
  produce is checked against what those examples froze.

## Behavioral evidence

Ordinary work records observed failures and deterministic acceptance checks in
durable evidence artifacts. Per-skill eval trees are not part of this
repository. Watching behavior fail before a change and pass after remains valid
evidence; record both.

## The release re-verification

A release repeats three checks on top of the gates: the per-client install
matrix in `INSTALL.md` is re-run against current client versions, the macOS
platform baselines are re-verified against Apple's availability data with
`examples/macos-screen/` as the corpus, and the version bump lands in
lockstep across every plugin manifest with the tag that makes it real. The
tag is the release; a version bump without it breaks every pinned install.

None of these gates move. That is what makes the validation repeatable: the
same commands, the same verdicts, the same refusals — on the first item a
repository ships and on the fiftieth.
